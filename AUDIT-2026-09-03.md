# 2 — Arrival secrets wall — a REAL hole, proven end to end — **HIGH**

I attacked as an attacker, not by checking the intended paths are closed. Every
intended path **is** closed — and there is an unintended one that is wide open.

## The primitive — plant a booking, for free

The bookings INSERT policy
(`20260901201957_harden_bookings_insert_host_and_status.sql`) lets **any
signed-in account** insert a `pending_payment` / unpaid booking on **any**
listing, naming the real host (public), with **any check-in date it chooses**.
Nothing requires the dates to be free, and nothing requires payment. That is a
legitimate step of the real checkout flow — but it means an attacker can
manufacture, at will, a booking row that says "this guest and this host are on a
booking together." **Proven on test**: signed in as an attacker with no
relationship to a victim listing, the insert (their own JWT, RLS applied — not
the service role) was **ALLOWED**, `status pending_payment`, `check_in` tomorrow.

Four surfaces then hand out secrets/PII on the strength of that row. Worst first.

## REACHED #1 — every host's contact + financial PII, over the public API — **the worst**

`profile_private` is the view the August audit built to hide hosts' private
columns behind "yourself, your counterparty, or an admin". Its **counterparty**
branch (`20260828234001_profiles_private_view.sql`) is:

```sql
or exists (select 1 from bookings b
   where (b.guest_id = auth.uid() and b.host_id = p.id)
      or (b.host_id = auth.uid() and b.guest_id = p.id))
```

**No status filter.** *Any* booking joining you and them qualifies — including a
planted unpaid one. The view is `grant select ... to authenticated`, so this is a
**direct PostgREST read — no app route involved** — and it exposes
`email, phone, residential_address, stripe_account_id, stripe_payouts_enabled,
payout_balance_owed`.

**Proven on test, end to end.** As the attacker, after planting the unpaid
booking, a single `from('profile_private').eq('id', hostId)` returned the host's:

```
email:               phhost-…@gallowayseed.test
phone:               0777-SECRET-…
stripe_account_id:   acct_FAKE_…
payout_balance_owed: 123.45
```

(`residential_address` was null only because my fixture didn't set one; the view
returns it identically.) **Then I deleted the planted booking and re-read: the
row came back `null`.** That is the causal proof — the booking is the key, and
nothing else. So: any signed-in account reads any host's home address, email,
phone, Stripe account id and outstanding payout balance, on demand. No window, no
UI, no forgery.

## REACHED #2 — any property's door code, wifi password and address — the one you'd feel first

`app/arrival/[bookingId]/page.tsx` lets you in if `booking.guest_id === you` (or
an active companion) — it selects `status` but never checks it — and `codeReady =
daysUntilCheckIn <= 3` comes from `stayCountdown`, which reads **only the dates**.
So the planted booking (check-in tomorrow, attacker's choice) renders the lot.

**Proven end to end.** Victim listing with door code `DOORCODE-A0I4XP` and wifi
password `wifisecret-a0i4xp`; attacker with no relationship to it; planted unpaid
booking; signed into the real UI; loaded the page. It rendered the **door code**,
the **wifi password**, exact address `1 Secret Lane, DG7 9ZZ`, arrival directions,
what3words, parking and host phone. The door code needs check-in within 3 days —
which the attacker picks — and the address/wifi/directions need **no window at
all**. Works against draft and hidden listings too. The whole `listing_arrival` /
`listing_access_codes` wall (grant-less tables, `can_listing`-checked routes) is
bypassed because the *page* reads both under the service role and gates only on
"is there a booking row with my id on it".

## REACHED #3 — address + what3words via the trips API

`/api/trips` (JSON, no page) attaches arrival essentials — **exact address,
postcode, what3words** — to **every** booking with `guest_id=you`, no status
filter (`app/api/trips/route.ts:31-35, 84-112`). Same planted booking, address
straight out. (Door code and wifi password are correctly page-only.)

## Not-REACHED, but same missing gate — `contactNumberVisible`

`lib/stayWindow.ts:contactNumberVisible` excludes only `cancelled`/`declined`,
**not** unpaid — so it treats the planted booking as a live upcoming stay and
would return the host's phone in `/api/messages/threads/[bookingId]`. I could
**not** land it there, but for a reason that is itself a finding, not a
protection: that route reads `profile_private` **with the service role**, for
which `auth.uid()` is null, so the view returns nothing and the route hands back
the generic name `"Host"` and `phone: null` — see the functional note below. The
phone still leaks, just through surface #1 (the direct `profile_private` read),
not this route.

### Why these four, and not the rest

Every *other* booking-scoped path gets the status check right: the
**scheduled-message sender** reads the door code only for `status='confirmed'`
bookings; the **trips card / home card** use `upcomingUntilCheckout`
(confirmed-only). The four above forgot it — and the profile_private one is the
same omission living in a **migration**, not app code, which is why it's the
easiest to miss and the worst to leave.

### The fix (report only — NOT applied; migration + code, not a broken render)

One idea, applied in every place: a booking grants access to secrets/PII only
once it is **real** — `status = 'confirmed'` (equivalently `payment_status =
'paid'`). Concretely:

- `profile_private`'s counterparty branch: add `and b.status = 'confirmed'` (or
  `and b.payment_status = 'paid'`). This is the one that matters most and it's a
  one-line migration — but it's the privacy view every host relies on, so it
  wants your eyes and a read-back on prod.
- The arrival page `allowed` check and the `/api/trips` arrival attach: require
  `booking.status === 'confirmed'`, matching `upcomingUntilCheckout`.
- `contactNumberVisible`: exclude anything not `confirmed`, not just
  cancelled/declined.

I did not touch any of it — it's money-/PII-path and wants your review.

### Functional note (not security): the messages panel shows "Host"/"Guest", not names

While proving #1 I found that `/api/messages/threads/[bookingId]` reads
`profile_private` with the **service role** (`createClient(URL, SERVICE_ROLE)`),
and that view is gated on `auth.uid()`, which is null for the service role — so
it returns **no row**. In my test the route returned `other.name = "Host"` and
`phone: null` for a real booking. Read as written, this panel can **never** show
the counterparty's real name or number; it falls back to the generic role label.
Worth confirming in the live `/messages` panel — if it shows "Host" instead of
the guest's name, this is why. (It also means the route doesn't leak the phone —
but the direct view read in #1 does, so that's cold comfort.) Report only.

## PROTECTED — every intended path, proven at the right layer

Kept apart from "my harness couldn't" — these were *reached* and *refused*:

- **Forged-cookie impersonation** (the technique from the August work): the
  arrival route, access-code route, trips route and booking-guests route all use
  `getUser()`, which verifies the JWT signature against the auth server. I proved
  it directly: `getUser(<forged JWT: victim sub + garbage signature>)` →
  `user=null, "invalid JWT: unable to parse or verify signature"`;
  `getUser(<real JWT>)` → the real user id. Forging the cookie buys nothing on
  these routes. (It's also moot — the hole above needs no forgery; a plain honest
  account gets in.)
- **Co-host without the listing permission**: `checkListing` returns null unless
  the specific `can_listing` flag is true on an *active* `listing_access` row —
  it reads the exact permission, not mere co-host existence
  (`lib/access.ts`). 403.
- **Companion (not the booker)**: two independent refusals. The `booking-guests`
  route only lets the **booker** (`guest_id`) invite, and an invitee becomes
  `active` only by accepting an emailed `invite_token`. And a direct
  `booking_guests` self-insert via RLS is **REFUSED (42501)** — proven on test
  (status `active`, self, arbitrary booking → refused; defaults → refused). So a
  companion genuinely can't self-appoint; the ones who see the code are the ones
  the booker added, by design.
- **The RSC payload** (the trap you flagged): outside the 3-day window the
  arrival page selects only `listing_id` from `listing_access_codes`, never
  `code` — the secret never enters the page's data or the streamed payload. Done
  correctly. (Inside the window the guest is entitled to it.)
- **Scheduled-message sender**: `CRON_SECRET`, fail-closed on a missing secret,
  header-only, before any DB work. Code read service-role-only, confirmed-only,
  and **never written to a log** — the held-back/error paths log the listing id
  and the DB error, never the body that carries the code.
- **error_log / admin error export**: the door code is never passed to
  `logError` on any path I traced, so it cannot appear in `/admin/errors` or its
  export. Not an exfil route for it.
- **Storage bucket**: the arrival secrets don't live in storage — not a path to

## The `cancellation_window_hours` question — answered

**It is read live, never snapshotted, and that is a landmine — but it is not
armed today.**

- The cancel route reads `service_providers.cancellation_window_hours` **at
  cancel time** (`orders/cancel/route.ts:93-97`), not a value frozen on the
  order. `guestMayCancelFree` gives a full refund only if `now` is more than
  `windowHours` before the service; a **larger** window means an **earlier**
  free-cancel cutoff.
- **What it means for an order placed before a provider changes their policy:**
  whatever number is current at cancellation governs — not the one the guest saw
  and agreed to at purchase. If a provider **raises** the window (48h → 120h),
  every guest who already booked loses free-cancellation time retroactively; a
  refund right they had at purchase can silently vanish.
- **Can a provider shorten a window a guest relied on *today*?** No — and this is
  the reassuring half. **Nothing can write `cancellation_window_hours`**: no app
  route sets it, and it is **not in the `authenticated` UPDATE grant** on
  `service_providers` (that grant is `sms_opt_out`, `status`/`confirmed_at`, and
  the five profile fields — verified in the migrations). So it is effectively
  immutable at its default 48 for every provider right now. A direct PostgREST
  PATCH is refused for lack of the column grant.
- **Why it still matters:** the field is per-provider, is shown to guests as
  "their cancellation window", and is plainly meant to become provider-editable
  in this phase. **The day an edit route or column grant ships, this becomes a
  live retroactive-policy hole** unless the value is frozen at purchase.
- **Fix (report only):** snapshot the applicable window onto `service_orders` at
  order creation and have the cancel route read the order's copy, not the
  provider's live row — the same "freeze the terms the guest agreed to" rule
  `bookings` already follows for `commission_rate` et al. Do this **in the same
  change** that first lets a provider edit the window, not after.

## Everything else on the path — verified sound

- **Slot engine / seat holds**: the seat is claimed by an **atomic
  compare-and-swap** on `slot_sessions.seats_taken` (update WHERE seats_taken =
  the read value), DB-serialised, before the card. Session (date, time) is
  validated server-side against the generated template and blocks, must fall in
  the stay, must be in the future — never trusted from the browser.
- **30-minute Checkout expiry**: `SLOT_HOLD_MINUTES = 30`. The Stripe Checkout's
  `expires_at` and the order's `expires_at` are both set to the hold edge, so an
  abandoned Checkout stops being payable at the same instant the seat frees. (30
  is also the floor Stripe allows for `expires_at` — a smaller value would have
  made every slot booking fail. The "15 minutes" in the `slots/book` header
  comment is a **stale comment**, not a bug — the constant is 30.)
- **No seat leak**: `cron/service-orders` sweeps both `authorised` holds (cancel
  the PI) and `holding` slot orders past expiry (with a grace window so it never
  races the webhook), releasing the seat on the latter, guarded on the status so
  a just-confirmed order is never expired.
- **Capture on confirm**: request-shape orders authorise with
  `capture_method: 'manual'` (card held, not charged); the money moves **only**
  when the provider confirms (`orders/respond` captures, keyed `capture-<id>`);
  decline/never-answer releases the hold untaken. The Stripe act always precedes
  the status write, so a row never reads `confirmed` while money is only held.
- **Merchant of record / fee**: every order is a destination charge
  `on_behalf_of` the provider with the platform 10% as an `application_fee` —
  the liability posture is correct and consistent.
- **Money never trusted from the browser**: price comes from the provider's own
  `service_provider_items` row; quantity is validated against the item's unit and
  capped; item price/unit/quantity are snapshotted onto the order.
- **Refunds**: both the guest free-cancel and the provider goodwill refund use
  `reverse_transfer: true` + `refund_application_fee: true`, keyed `refund-<id>`,
  and only `confirmed → refunded`; a slot's seat reopens on refund.
- **The exclusive-per-date race is handled**: two guests can both pass the
  request-time clash pre-check for a chef; the partial unique index rejects the
  second at webhook insert, and the webhook **cancels that guest's held
  PaymentIntent** (`cancel-race-<pi>`) rather than leaving a 7-day hold on a card
  for an evening they didn't get.

### `profiles.full_name` ignores `show_full_name` — STILL TRUE at the layer that matters

**Proven on test:** the **anon** key read `full_name = "AUDITNAME-…"` for a
