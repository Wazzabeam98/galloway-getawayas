## How to read the verdicts

Two failure shapes look identical from the outside and are kept apart on purpose:

- **REACHED** — I built the request a real attacker would, it reached the thing
  it targets, and it got the secret / did the write. A finding, proven.
- **PROTECTED** — same: the request *reached* the gate and the right layer
  refused it. Proven, not assumed from reading one file.
- **HARNESS-BLOCKED** — I could not land the request end to end (cookie wire
  format, a stale preview). A limit of my rig, **not** evidence of safety.

The preview deployment is **262 commits behind master** and still runs the old
code for several of these routes, so it was useless as a test target for
master's behaviour. Everything below was proven against a **local dev server on
master, pointed at the test project** — the only way to exercise master's code.

# 1 — `services/apply` squatting — ALREADY FIXED on master (was: still open)

**Verdict: the exact fix you described is implemented and live on master.** Your
task, and `OUTSTANDING.md`, describe the route as still creating an auth user on
the first press. It does not any more.

Commit `5543cd3` "Prove the address before the account exists (#73)" (1 Sep)
rebuilt the join flow into precisely the shape you said you wanted:

- **`/api/services/apply`** now writes the application into `service_applications`
  and mints a token — **it creates no account**. I read every account-creation
  call in the services path: the only `auth.admin.createUser` is in `/finish`.
- **`/api/services/finish`** creates the account, and only when the emailed,
  single-use token's hash matches an `service_applications` row that is unclaimed
  and unexpired. The token goes only to the address's mailbox, so proving receipt
  = proving ownership. This is "don't create the account until the address is
  proved", built as a join-flow change, not a guard in front of the old flow.
- `service_applications` has **RLS on and no policies at all**, grants revoked —
  PostgREST won't admit it exists to a browser role. (Migration
  `20260901170000_an_application_is_not_an_account.sql`.)
- The email-existence oracle is closed: apply returns the **same** response
  whether or not an account exists; the difference is carried only in the email.

### What a stranger can still do to it today (residual, LOW)

Unauthenticated, a stranger can still:

1. **Send up to 2 "verification"/"already-applied" emails per day to a chosen
   address** (a low-grade harassment / phishing-lookalike primitive), and write
   junk rows into `service_applications` that populate the admin chase list.
2. **Consume the shared mail allowance**, bounded by the global limit.

**Does the rate limit meaningfully change the squatting risk?** It never was the
thing standing between a stranger and a squat — the *account* is. With the
account gone from this route, the rate limit's remaining job is purely
volume/mail-quota (global 20/hr is the load-bearing one; per-IP 3/hr is close to
decorative since the caller picks their own address; per-email 2/24h caps the
harassment-email rate at a chosen victim). None of the three touches squatting,
because squatting is no longer reachable here.

**Cost to fully close the residual:** small, and probably not worth it before
launch — the account squat, the thing that mattered, is already closed. If you
want the harassment-email vector gone too, the lever is the per-email cap (drop
2/24h → 1, or require the email to not already have a *pending unclaimed
application* before sending another). Report only — I changed nothing.

# 2 — Arrival secrets wall — a REAL hole, proven end to end — **HIGH**

I attacked as an attacker, not by checking the intended paths are closed. Every
intended path **is** closed — and there is an unintended one that is wide open.

## REACHED — any free account reads any property's door code, wifi password and exact address

**The arrival page trusts the *existence* of a booking row, never its status.**
`app/arrival/[bookingId]/page.tsx` lets you in if `booking.guest_id === you` (or
you're an active companion) — it selects `status` but never checks it. And the
reveal window (`codeReady = daysUntilCheckIn <= 3`) is computed from
`stayCountdown`, which reads **only the dates**, never the status either.

Meanwhile the bookings INSERT policy
(`20260901201957_harden_bookings_insert_host_and_status.sql`) lets **any
signed-in account** create a `pending_payment` / unpaid booking on **any**
listing, naming the real host (which is public), with **any check-in date it
chooses**. Nothing requires the dates to be available, and nothing requires
payment.

Chain them:

1. Attacker signs up (automatic) → free account.
2. Reads the target listing's `host_id` (public).
3. Inserts a booking: `guest_id=self, host_id=<real host>, status='pending_payment',
   check_in=tomorrow`. **RLS allows it.**
4. Opens `/arrival/<bookingId>`.

**Proven on test, end to end.** I created a victim listing with door code
`DOORCODE-A0I4XP` and wifi password `wifisecret-a0i4xp`, a separate attacker
account with no relationship to it, inserted the unpaid booking **as the attacker
(their JWT, RLS applied — not the service role)**, signed the attacker into the
real UI, and loaded the arrival page. It rendered:

- **Door code: `DOORCODE-A0I4XP`** ("Shown because your check-in is close")
- **Wifi password: `wifisecret-a0i4xp`**, exact address `1 Secret Lane, DG7 9ZZ`,
  arrival directions ("turn left at the oak"), what3words, parking, host phone.

The door code needs check-in within 3 days — but the attacker *picks* the date,
so that's always satisfied. The address / wifi / directions / what3words need
**no window at all** — they render for any pending booking on any date. This
works against draft and hidden listings too, not just published ones.

**This is the whole point of the wall, bypassed.** `listing_arrival` and
`listing_access_codes` are grant-less tables reachable only through routes that
check `can_listing` — and the audit comments in those routes are proud of it.
The arrival *page* reads both tables under the service role and gates on nothing
but "is there a booking row with my id on it", which any account can manufacture.

### Second surface, same root cause — REACHED

`/api/trips` (JSON, no page needed) attaches arrival essentials — **exact
address, postcode, what3words** — to **every** booking with `guest_id=you`,
with no status filter (`app/api/trips/route.ts:31-35, 84-112`). The same planted
unpaid booking leaks the address and what3words straight out of the API. (Door
code and wifi password are correctly *not* on this route — those are page-only.)

### Why it's the outlier

Every *other* code-touching path gets the status check right. The
**scheduled-message sender** only ever reads the code for `status='confirmed'`
bookings and only writes it into the confirmed guest's own thread; the **trips
card / home card** use `upcomingUntilCheckout` (confirmed-only). The arrival page
and the trips-route arrival block are the two that forgot.

### The fix (report only — NOT applied; it's a code change, not a broken render)

Gate both on payment/confirmation: the arrival page's `allowed` and the trips
route's arrival attach should require `booking.status === 'confirmed'` (matching
`upcomingUntilCheckout`). One condition each. It's money-adjacent physical
security (a door code), so it wants your eyes on the diff — I did not touch it.

## PROTECTED — every intended path, proven at the right layer

Kept apart from "my harness couldn't" — these were *reached* and *refused*:

- **Forged-cookie impersonation** (the technique from the August work): the
  arrival route, access-code route, trips route and booking-guests route all use
  `getUser()`, which verifies the JWT signature against the auth server. I proved
  it directly: `getUser(<forged JWT: victim sub + garbage signature>)` →
  `user=null, "invalid JWT: unable to parse or verify signature"`;
  `getUser(<real JWT>)` → the real user id. Forging the cookie buys nothing on
  these routes. (It's also moot — the hole above needs no forgery; a plain honest
  account gets in.)
- **Co-host without the listing permission**: `checkListing` returns null unless
  the specific `can_listing` flag is true on an *active* `listing_access` row —
  it reads the exact permission, not mere co-host existence
  (`lib/access.ts`). 403.
- **Companion (not the booker)**: two independent refusals. The `booking-guests`
  route only lets the **booker** (`guest_id`) invite, and an invitee becomes
  `active` only by accepting an emailed `invite_token`. And a direct
  `booking_guests` self-insert via RLS is **REFUSED (42501)** — proven on test
  (status `active`, self, arbitrary booking → refused; defaults → refused). So a
  companion genuinely can't self-appoint; the ones who see the code are the ones
  the booker added, by design.
- **The RSC payload** (the trap you flagged): outside the 3-day window the
  arrival page selects only `listing_id` from `listing_access_codes`, never
  `code` — the secret never enters the page's data or the streamed payload. Done
  correctly. (Inside the window the guest is entitled to it.)
- **Scheduled-message sender**: `CRON_SECRET`, fail-closed on a missing secret,
  header-only, before any DB work. Code read service-role-only, confirmed-only,
  and **never written to a log** — the held-back/error paths log the listing id
  and the DB error, never the body that carries the code.
- **error_log / admin error export**: the door code is never passed to
  `logError` on any path I traced, so it cannot appear in `/admin/errors` or its
  export. Not an exfil route for it.
- **Storage bucket**: the arrival secrets don't live in storage — not a path to
  the code. (The bucket has its own, separate issue; see task 8.)

# 5 — `as any` / type opt-out census — the number is bigger than the casts

**Headline: there are no generated Supabase types at all.** `types.ts` is
hand-written with row shapes literally typed `id: any; price: any; …`, and
**every** Supabase client is created untyped — ~30 `createClient` /
`createClientComponentClient` call sites, **none** passing a `<Database>`
generic. So `.from('x').select(...)` is `any`-shaped everywhere: the compiler
cannot catch a wrong column on a query result **anywhere** in the project. The
casts are the visible tip of a data layer that is already fully opted out.

Counts (app+lib+components / whole repo): `as any` ~50 / 83 · `as unknown as` 7 ·
`@ts-ignore` 2 · `@ts-expect-error` 0 · `: any` annotations ~1280 (scale, not
1280 distinct holes) · `any[]` 166 · `Record<string, any>` 70 · `x: any = <row>`
row-aliases 29 · `eslint-disable` 33.

The dangerous category (a wrong column ships silently and blanks a guest/money
line — today's shipped bug), ranked worst-first:

1. `components/UpcomingTrip.tsx:72` — `(booking as any).cleaning_fee` →
   `cancellationPosition()` → the **refund figure on the home-page trip card**.
   Money + guest-facing.
2. `app/trips/page.tsx:425` — the same `(b as any).cleaning_fee` on the Trips
   list. One typo blanks both. **⚠ follow-up below.**
3. `app/arrival/[bookingId]/page.tsx:80` — `(access as any).code` (door code;
   blank ⇒ guest can't get in).
4. same file:102 — `(host as any).phone` (arrival contact).
5. same file:78 — `const l: any = listing` then address/postcode/coords.
6. `lib/serviceProviders.ts:929/935/936` — provider hourly rate / bands (money).
7. `app/api/services/orders/respond/route.ts:130/169` — `order.status as any`
   into `canTransition()` (a bad value skips the guard instead of erroring).
8–12. experience-order address, `notify` dynamic column, sitemap, listing-save
   audit diff, provider prefill — lower stakes.

**Follow-up I ran because of #1/#2:** `cleaning_fee` **is** a real column on
`listings` (confirmed against the live schema). I have **not** yet confirmed it
exists on **`bookings`**, which is the table those two casts read — if it
doesn't, that refund figure is silently wrong *today*. Flagged for the money-path
work (task 3).

**Size, plainly:** it's not "83 casts", it's "the type system was never told
what the database looks like". Generating `Database` types and passing
`<Database>` to the clients converts categories 1 and the 29 row-aliases from
silent blanks into compile errors — which is exactly what caught the *typed* one
of today's two bugs. Not a tonight job; the biggest single lever against the
whole class.
